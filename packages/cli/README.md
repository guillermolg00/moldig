# moldig

**CleanMyMac for your AI setup.** Six AI coding harnesses — Claude Code, Codex, Cursor, Gemini
CLI, Copilot and OpenCode — each keep their own configuration and their own state on your
machine: context files you wrote, skills installed through several installers into a dozen
harness directories at once, MCP servers configured in five different files, memory files a
harness writes for itself, and hundreds of megabytes of harness cache. Nothing shows all of it
in one place, and nobody can tell you what one session in the project you are standing in costs
you in tokens.

moldig reads all of it, in one pass, and shows you what is there, what it costs and what is
worth removing.

```sh
npx moldig            # the interactive experience
npx moldig scan       # what every harness left on this machine
npx moldig audit      # the headline number and the findings
npx moldig clean      # remove the harness-owned items you select
```

Requires Node.js 22.18 or newer.

> **Today**: `scan` and `audit` are complete for Claude Code. The other five harnesses are on
> the way, `clean` refuses to remove anything until the actions engine lands, and the interactive
> experience arrives with it. moldig always says which harnesses it read and never pretends to
> have removed anything.

## Install

```sh
npx moldig            # no install
npm i -g moldig       # or keep it around
```

The published package is a single file that bundles the engine, with no runtime dependency
today (the trash helper `clean` needs cannot be bundled and will be the only one). The engine is
published separately as [`@moldig/core`](https://www.npmjs.com/package/@moldig/core).

## What it finds

| | |
|---|---|
| **Context files** | `CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, Cursor rules — which harness loads which, fully, on demand or never |
| **Skills** | one row per real directory, with every harness that reaches it, its origin and whether it drifted from it |
| **MCP servers** | every entry in every configuration file, with duplicates and exposed secrets |
| **Memory files** | what a harness wrote about a project for itself, its size in tokens, and (Claude Code) which facts were never read |
| **Harness cache** | transcripts, tool results, shell snapshots, plugin clones — grouped by the unit the harness documents as safe to sweep |
| **Projects** | every directory a harness ever worked in, including the ones whose directory is gone |

## Commands

### `moldig [roots…]`

The interactive experience: scan, overview, drill-down, selection, confirm, result. In a pipe it
prints the `audit` output and exits 0.

### `moldig scan [roots…]`

The read-only pass. Prints one row per harness with its presence and its counts, the projects
with what a session there loads, the totals, and the stray and unreachable counts. With `--json`
it prints the index document (`schemaVersion: 0`) and nothing else.

Exit codes: `0` the scan completed (warnings do not change it) · `2` usage or environment error.

### `moldig audit [roots…]`

Scan, then the detectors. Prints the headline number per harness — *every session pays X +
`<project>` adds Y = Z tokens/session* — the eight categories with their counts and severity, and
the findings table. With `--json` it prints the index document plus `findings[]` and `headline`.

| Flag | |
|---|---|
| `--fail-on low\|medium\|high\|never` | exit 1 on a finding at this severity or above (default `low`) |
| `--category <c>` | `duplicate`, `orphan`, `bloat`, `drift`, `shadow-memory`, `autogenerated`, `harness-cache`, `exposure`; repeatable |
| `--severity low\|medium\|high` | keep that severity and above |
| `--no-read-signal` | skip the memory read signal; never-read facts stay unknown |

`--category` and `--severity` restrict the table, the JSON `findings[]` and what `--fail-on`
looks at. The headline and the index parts are never filtered.

Exit codes: `0` nothing at or above `--fail-on` · `1` something is · `2` usage or environment
error. In CI:

```sh
npx moldig audit --fail-on high    # fails the build on a high-severity finding, e.g. an
                                   # exposed secret in a git-tracked .mcp.json
```

### `moldig clean [roots…]`

Scan, then remove the harness-owned items you select. In a terminal it opens the selection panel.
Unattended it needs **both** `--yes` and a filter, so a scheduled run can never remove more than
it was told to.

| Flag | |
|---|---|
| `--yes` | run unattended; a filter is required with it |
| `--category harness-cache` | the only category an unattended clean reaches in v1 |
| `--older-than <days>` | keep only units older than this |
| `--dry-run` | print the plan and stop; nothing is moved |

Exit codes: `0` every attempted row succeeded · `1` a row failed · `2` refused to run, or usage
or environment error.

### Shared flags

| Flag | |
|---|---|
| `[roots…]` | limit the scan to the projects under these directories |
| `--harness <id>` | `claude-code`, `codex`, `cursor`, `gemini-cli`, `copilot`, `opencode`; repeatable |
| `--no-git` | never spawn git; git-tracked status stays unknown |
| `--json` | the machine-readable document on stdout and nothing else |
| `--pretty` | indent the JSON; implies `--json` |
| `--help`, `--version` | |

Warnings always go to stderr, one line each, and into `warnings[]` in the JSON. `NO_COLOR`,
`FORCE_COLOR` and `TERM=dumb` are honoured.

## What moldig promises

- **The scan is read-only.** It never runs a harness, a sub-agent or an MCP server, and it never
  writes anything — no configuration file, no cache, no data directory. The only process it
  spawns is `git ls-files`, once per repository, to learn what is tracked.
- **Every removal is recoverable.** Files, directories and links go to the OS trash. A
  configuration or lock file is copied to a backup before an entry is edited, and the backup path
  is printed. What moldig does not understand it never rewrites: it delegates to the harness's own
  command. On a volume without a working trash, nothing is removed and moldig says why.
- **Every run is recorded.** A clean or delete run writes a manifest listing each target, where it
  went and how it ended, and prints its path.
- **Nothing is written inside a repository.** No backups, no manifests, no cache files — moldig
  never dirties your git status.
- **The network is touched once, on demand**: the preview of what an update would change. Nothing
  else leaves the machine.
- **No telemetry, no account, no daemon, no configuration file.** The first run is `npx moldig`
  and nothing else.
- **No file contents in the output.** Transcripts are read for paths and timestamps only,
  credential stores are never opened at all, and no secret value ever reaches the screen or the
  JSON.
