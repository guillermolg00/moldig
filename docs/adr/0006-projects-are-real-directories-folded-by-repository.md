# Projects are real directories folded by repository; breadcrumbs are evidence, not identity

Every harness records where it has worked in its own way: Claude Code keys `~/.claude.json` by absolute path and names transcript directories with a lossy slug, Codex keeps trust tables in `config.toml` and a working directory per session, Cursor and VS Code keep one workspace record per opened folder, Copilot a trusted-folders list, OpenCode a project table, Gemini CLI nothing at all. On the reference machine 35–92 % of those records point at directories that no longer exist, several point at `~`, `/` or `~/Work`, and sessions started in a subdirectory or a worktree of a repository leave their own record while the harness itself routes memory to the repository. The easy design makes every record a project: faithful to each harness and trivial to implement, but it would show one codebase as five rows, `~` as a project with a dozen projects inside it, and hundreds of ghosts as peers of the real work. We decided instead that a **Project is a real directory** (its `realpath`, compared case-insensitively where the filesystem is), **folded to the repository directory** (subdirectory and worktree breadcrumbs belong to the repository's Project), and only when the directory **is a repository or carries harness configuration**; whatever a harness wrote about a bare directory is **Stray** under that harness's user scope, a missing directory is an **Orphan**, and a directory on an unmounted volume is **Unreachable**. A breadcrumb is evidence that a harness worked somewhere; it never defines what a project is. The reason is the unit of action: users think in codebases, and `clean`/`delete` must operate on one row that gathers what N harnesses left about one codebase. The unified index (ticket 07) freezes this shape, which is what makes the choice hard to reverse.

## Consequences

- Discovery reads breadcrumbs from every harness's user scope and resolves them to real directories. A Project carries N breadcrumbs, one per harness record, and a kind: repository, detached worktree (its `.git` pointer is broken), plain directory with markers, or unknown (the directory is gone); an intact linked worktree is a member of its repository's Project, never a kind of its own.
- Subdirectory and worktree breadcrumbs never create Projects; their state is attributed to the repository's Project. A repository nested in a non-repository, or in another repository (submodule), is a Project of its own. Worktrees are resolved by reading the `.git` file; discovery spawns no process (`git` is only invoked later, for git-tracked status).
- `~`, `/` and other bare directories never appear as Projects. Their harness state is Stray: listed and cleanable under the harness's user scope, never preselected when it is memory.
- Missing directories are Orphan findings pointing at both the breadcrumb and the harness-owned state behind it; targets on unmounted volumes are Unreachable and untouched. Discovery does not guess whether a project moved.
- Amended 2026-08-25 (ticket 07): a directory that is gone keeps its Project — identified by the recorded path, since neither `realpath` nor the repository/configuration test can run, the one case where breadcrumbs alone name a Project — with reachability *orphan* and kind *unknown*, so the Orphan finding has one subject gathering what every harness left about it; such Projects are shown apart from present ones, never mixed with them.
- An optional Root (0..n) narrows the scan to the Projects under it and adds a bounded marker walk; a Root inside a Project selects that Project whole. Without a Root, the Project enclosing the working directory is always included.
- Gemini CLI leaves no breadcrumb on the reference machine; its Projects come from the marker walk and from documented sources tested against fixtures.
- Discovery runs on every scan (no cache) and stays under a second on the reference machine because it prefers each harness's cheap, authoritative source (SQLite through `node:sqlite`, JSON/TOML keys) over per-file transcript scans.
- Under WSL moldig is plain Linux: it scans the distro's own home only. Reading the Windows side (or a distro from Windows) is deferred; when it comes, the same rule applies — one Project per real directory after path translation.
